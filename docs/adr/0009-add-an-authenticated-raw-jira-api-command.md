# Add an authenticated raw Jira API command

jiro provides `jiro api <endpoint>` as a controlled escape hatch for one authenticated HTTP request to a relative endpoint of the selected Jira Instance. It reuses the effective Profile, atomic environment Credential override, User-Agent, and Jira context path without an authentication preflight. Absolute and scheme-relative endpoints are rejected; other URL syntax is delegated to URL construction and Go's HTTP stack. Explicit methods are trimmed, uppercased, and passed through without an allowlist, while `read_only` Profiles permit only GET, HEAD, and OPTIONS.

An API Request deliberately streams Jira-owned response bytes instead of jiro's normalized text or JSON. Successful 2xx bodies go unchanged to stdout; unsuccessful bodies go unchanged to stderr with the existing status-based exit codes. Global `--output` is unsupported, `--quiet` suppresses only a successful body, and `--include` prepends deterministic metadata visible after Go's normal response processing without redacting `Set-Cookie`. Redirects are disabled and 3xx responses are raw API errors. Requests stay on HTTP/1.1, use standard Go compression and keep-alive semantics, and add no application-level retry, pagination, cache, formatting, or endpoint-specific behavior.

Fields and multipart inputs retain their body-construction grammar without a 16 MiB field limit or explicit UTF-8/control-character validation. `encoding/json` owns invalid UTF-8 replacement. GET, HEAD, and OPTIONS fields become ordered query parameters while `--input` and `--form` may still supply request bodies. Protected headers remain case-insensitive; other header names and values are left to Go, repeated values preserve command-line order, and an empty value clears earlier values.

This decision supersedes ADR 0007's normalized-output-only rule for `jiro api` and no other command. Typed commands keep singular grammar and normalized output, `contractVersion` remains `3`, and the JSON envelope `schemaVersion` remains `1`. Arbitrary transport paths do not add Jira Cloud REST API v3 compatibility; Jira Data Center and Server REST API v2 remain the canonical platform.
