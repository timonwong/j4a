# Add an authenticated raw Jira API command

jiro provides `jiro api <endpoint>` as a controlled escape hatch for one authenticated HTTP request to a safe relative endpoint of the selected Jira Instance. It reuses the effective Profile, Credential, authentication type, connection overrides, and Jira context path without an authentication preflight. The command accepts an allowlisted HTTP method, streaming input, ordered JSON-or-string fields, multipart form data, request headers, a timeout, invocation-scoped insecure TLS, and final response headers. Relative endpoint validation rejects alternate origins, fragments, traversal, backslashes, and control characters before Credential resolution or network access; `read_only` Profiles permit only GET, HEAD, and OPTIONS.

An API Request deliberately streams Jira-owned response bytes instead of jiro's normalized text or JSON. Successful 2xx bodies go unchanged to stdout; unsuccessful bodies go unchanged to stderr with the existing status-based exit codes. Global `--output` is unsupported, `--quiet` suppresses only a successful body, and `--include` prepends deterministic final response metadata with `Set-Cookie` values redacted. Only bodyless GET and HEAD may follow at most five same-origin redirects. jiro does not retry, paginate, cache, format, or add endpoint-specific request behavior.

This decision supersedes ADR 0007's normalized-output-only rule for `jiro api` and no other command. Typed commands keep singular grammar and normalized output, `contractVersion` remains `3`, and the JSON envelope `schemaVersion` remains `1`. Arbitrary transport paths do not add Jira Cloud REST API v3 compatibility; Jira Data Center and Server REST API v2 remain the canonical platform.
